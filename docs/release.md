# Tack Release Process

**English | [简体中文](release.zh-CN.md)**

This document describes Tack's versioning and cross-platform packaging
process. Packaging is fully automated by GitHub Actions
(`.github/workflows/tack-release.yml`); the release artifacts are consumed by
the `tack update` self-update command (conventions in
`crates/tack-app/src/self_update.rs`).

## 1. Release Conventions

| Item | Convention |
|---|---|
| tag format | `tack-vX.Y.Z` (e.g. `tack-v0.8.0`) |
| version location | `workspace.package.version` in `Cargo.toml` (single source of truth) |
| asset naming | `tack-<target-triple>.tar.gz` (Linux/macOS), `tack-<target-triple>.zip` (Windows) |
| archive contents | a single binary at the root: `tack` (Unix) or `tack.exe` (Windows) |
| checksum file | `SHA256SUMS.txt` |

The version in the tag must match `workspace.package.version` **exactly**, or
the workflow's prepare stage fails immediately. This is deliberate fail-safe
design: `tack update` matches the current platform via the target triple in
the asset name and compares versions via the version in the tag — neither can
be wrong.

Target platform matrix (6 targets):

| target triple | runner | notes |
|---|---|---|
| `x86_64-unknown-linux-gnu` | `ubuntu-latest` | |
| `aarch64-unknown-linux-gnu` | `ubuntu-24.04-arm` | native ARM runner, free for public repos |
| `x86_64-apple-darwin` | `macos-15-intel` | macos-13 is retired, do not use |
| `aarch64-apple-darwin` | `macos-latest` | Apple Silicon |
| `x86_64-pc-windows-msvc` | `windows-latest` | |
| `aarch64-pc-windows-msvc` | `windows-latest` | cross-compiled (the image ships the ARM64 MSVC toolchain) |

When changing the platform matrix, you must also update `target_triple()` in
`self_update.rs`, or users on that platform will be unable to self-update.

## 2. Standard Release Steps

```bash
# 1. Make sure main is green (CI passing, clean working tree)
git switch main && git pull

# 2. Local preflight — commands identical to ci.yml. Pushing a tag does
#    not trigger ci.yml, so format/lint issues would only surface after
#    tagging; always run these locally first.
cargo fmt --all -- --check
cargo clippy --locked --workspace --all-targets -- -D warnings

# 3. Bump the version: edit workspace.package.version in Cargo.toml
#    e.g. 0.8.0 → 0.9.0

# 4. Update CHANGELOG.md (user-visible changes)

# 5. Commit the version bump
git add Cargo.toml CHANGELOG.md
git commit -m "release: v0.9.0"
git push

# 6. Tag and push (triggers the packaging workflow)
git tag tack-v0.9.0
git push origin tack-v0.9.0
```

After pushing the tag, the workflow runs three stages automatically:

1. **prepare** — verifies the tag version matches `Cargo.toml`, checks the
   CHANGELOG entry, runs the fmt + clippy preflight (fail fast, to avoid
   wasting the 6-platform parallel build), and creates the GitHub Release
   (release notes are auto-generated by `--generate-notes` and can be edited
   afterwards on the web)
2. **build** — 6 platforms in parallel:
   `cargo build --release --locked --package tack-app`, each packaged as a
   tar.gz / zip
3. **publish** — collects the artifacts, generates `SHA256SUMS.txt`, uploads
   them to the Release

The whole run takes about 10–20 minutes (longer without caches). When it
finishes, check `https://github.com/<owner>/<repo>/releases` for all 7 assets
(6 archives + `SHA256SUMS.txt`).

## 3. Other Trigger Methods

### Re-releasing an existing tag

The tag already exists but needs repackaging (e.g. after a workflow fix):

1. Delete the old Release on the GitHub web UI (no need to delete the tag)
2. Actions → "Tack release" → Run workflow → enter the tag name (e.g.
   `tack-v0.9.0`)

workflow_dispatch checks out the code at that tag and builds it, with the same
version-match validation.

### Notes for private forks

- The `ubuntu-24.04-arm` native ARM runner is free only for public repos.
  Private repos must replace it with `ubuntu-latest` +
  [`cross`](https://github.com/cross-rs/cross) cross-compilation, or use
  cargo-zigbuild.
- `tack update` pulls from `DEFAULT_UPDATE_REPO` (`Tack-AI/tack`) by default.
  When a fork publishes its own packages, users must point at the fork repo
  via the `TACK_UPDATE_REPO=<owner>/<repo>` environment variable or the
  `updateRepo` setting.

## 4. Verifying a Release

After the release completes, verify the self-update path with an older binary:

```bash
tack update --check   # should show the new version and the asset name for your platform
tack update           # downloads, verifies --version runs, replaces the binary
tack --version        # should show the new version
```

You can also verify archive integrity manually:

```bash
curl -sLO https://github.com/<owner>/<repo>/releases/download/tack-v0.9.0/tack-x86_64-unknown-linux-gnu.tar.gz
curl -sL https://github.com/<owner>/<repo>/releases/download/tack-v0.9.0/SHA256SUMS.txt | grep x86_64-unknown-linux-gnu
sha256sum tack-x86_64-unknown-linux-gnu.tar.gz   # compare with the line above
```

Finally, refresh the ACP registry draft
(`assets/acp-registry/tack/agent.json`): bump `version` and the tag in every
archive URL to the new release, and replace the sha256 values with the ones
from the published `SHA256SUMS.txt`, so the draft stays submission-ready
(see `assets/acp-registry/README.md`).

## 5. Troubleshooting

| Symptom | Cause and fix |
|---|---|
| prepare stage reports "tag does not match workspace.package.version" | the tag version doesn't match Cargo.toml. Delete the tag (`git push origin :tack-vX.Y.Z`), fix the version, and re-tag |
| prepare stage fmt/clippy fails | the tagged code didn't pass preflight (step 2 was skipped before the release). Merge the fix into main, delete the tag, and re-tag — or fix and re-release via workflow_dispatch |
| one platform's build fails | a single matrix leg failing doesn't affect the others (`fail-fast: false`), but publish fails due to the missing artifact. Fix and re-release via workflow_dispatch |
| `tack update` can't find the asset | check that the asset name matches `asset_name()` in `self_update.rs`; check that the Release is in the `tack-v*` series (the `/releases/latest` endpoint is not used) |
| macOS x86_64 leg stuck in queue | make sure you're using `macos-15-intel`, not the retired `macos-13` |
| Cargo.lock-related build failure | the workflow uses `--locked`; before releasing, make sure `cargo build --locked` passes locally and Cargo.lock is committed |

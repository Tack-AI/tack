# 遥测与数据收集：设计决策

**[English](telemetry.md) | 简体中文**

**状态：已决定 —— Tack 不附带任何形式的遥测。**

## 决策

Tack 不收集、不传输、不上报任何使用数据、崩溃报告、指标或分析数据。
代码库中不存在遥测端点，也没有任何构建期或运行期开关可以启用它。

## 理由

- **默认隐私。** 编码代理处在一个异常敏感的位置：它会读取源代码（往往
  是专有或机密的）、shell 历史、文件路径、与凭据相邻的配置，以及用户
  prompt 的完整文本。来自这类工具的哪怕是"匿名"遥测，也可能泄露用户
  从未打算分享的信息 —— 一条堆栈跟踪可以内嵌文件路径，一个功能使用
  事件可以暴露某个秘密项目的存在。
- **信任。** 用户应当能够在敏感代码库上运行代理，而不必靠审计网络流量
  来获得安全感。"无遥测"是一条易于表述、易于验证、也不可能被误解的
  属性 —— 这与"遥测已匿名化"或"你可以退出"截然不同。
- **简单。** 没有同意流程，没有数据保留问题，没有合规表面积。

## 我们的替代方案

故障排查依赖严格的本地、用户可控的机制：

- **`tack doctor`** —— 环境自检（认证状态、provider 配置、沙箱支持、
  路径），由用户自行运行并可粘贴进 bug 报告。这就是 bug 报告 issue
  模板要求附上其完整输出的原因。
- **`~/.tack/agent/crash.log`** —— panic 会自动记录到这个本地文件。
  除非用户主动选择分享其中片段，否则它永远不会离开本机。
- **可选开启的本地 tracing** —— 在 settings 中设置
  `observability.enabled`（或 `TACK_TRACE_FILE=1`）会把代理活动的
  本地 JSONL trace 写出来用于调试。默认关闭，只写本地磁盘，完全处于
  用户控制之下。

## 代价（如实承认）

盲飞是一个真实的权衡：

- 我们**无法测量真实世界的崩溃率** —— 只能依靠愿意花时间提交 issue
  并附上 `crash.log` 的用户来了解崩溃。
- 我们**没有功能使用数据** —— 关于投入方向的决策（哪些 provider、
  哪些工具、哪些 TUI 功能）由 issue 数量、讨论和维护者判断驱动，而非
  关于用户实际行为的证据。

我们接受这些代价，作为隐私保证的价格。

## 未来任何可选开启的崩溃上报必须满足的条件

如果项目有一天考虑加入崩溃上报，以下条件必须全部满足 —— 少任何一条
都是对本决策的倒退：

1. **仅限显式开启（opt-in）。** 默认关闭；启用需要用户做出肯定性的
   动作（一个 settings key），绝不能是"跳过即保持开启"式的默认值。
2. **最小化负载。** 只包含 panic 位置（crate、函数、行号）、Tack 版本、
   平台/架构。**不含代码、不含文件路径、不含 prompt 或工具输出内容、
   不含 OS 家族之外的环境细节。** 负载内容必须有文档且可检视。
3. **服务端开源。** 接收端点的服务器软件必须开源，以便用户能核实究竟
   存储了什么、如何存储。
4. **随时可撤销。** 用户可以随时关闭它，且关闭必须立即停止一切传输。

在这样的机制存在并满足全部四个条件之前，"Tack 会回传数据吗？"的答案
依然很简单：**不会。**
